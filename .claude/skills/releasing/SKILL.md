# Releasing Whisper Master

The hard prohibitions from this workflow also live in `CLAUDE.md` (§ Release safety
rules) because they must be in context even when this skill is not loaded. They are
repeated here in their full original form.

### Signing & keys (Developer ID + notarization)

- **Code signing:** a **Developer ID Application** cert (Team ID `7MFYAGK3VV`, "subrahmanya s hegde"), created in Xcode → Settings → Accounts → Manage Certificates → + → *Developer ID Application*. `bundle.sh` & `release.sh` default `SIGN_IDENTITY="Developer ID Application"`; pass `SIGN_IDENTITY=-` for an ad-hoc local build. The build enables the **hardened runtime** (`ENABLE_HARDENED_RUNTIME: YES` in `project.yml`) with `Resources/WhisperMaster.entitlements` (only `com.apple.security.device.audio-input` — non-sandboxed; text injection uses Accessibility/TCC, Bonjour needs no entitlement). `bundle.sh` also passes `--timestamp` (secure timestamp, required by notarization) and `CODE_SIGN_INJECT_BASE_ENTITLEMENTS=NO` (so the debug-only `get-task-allow` is never injected — the notary service rejects it). The old self-signed **`whisper master`** cert is retired.
- **Notarization:** `Scripts/notarize.sh <path-to-.app-or-.dmg>` submits to Apple's notary service (`xcrun notarytool submit --wait`) and staples the ticket (`xcrun stapler staple`). `release.sh` notarizes+staples the `.app` *before* zipping (the ticket travels in the Sparkle zip); `make-dmg.sh` staples the `.app` then the `.dmg`. **Credentials** (first match wins, read from env / `.env`): `NOTARY_KEY_P8`+`NOTARY_KEY_ID`+`NOTARY_ISSUER` (App Store Connect API key), or `NOTARY_PROFILE` (a name saved once via `xcrun notarytool store-credentials`), or `NOTARY_APPLE_ID`+`NOTARY_PASSWORD`+`NOTARY_TEAM_ID`. If none are set, notarization is **skipped** (build still produced, just not notarized). Notarized + stapled means **no more first-launch `xattr -dr com.apple.quarantine`** — installs and DMG mounts are warning-free.
- **Update signing:** a Sparkle **EdDSA** keypair (Sparkle's `bin/generate_keys`; private key lives in the login keychain, public key is `SUPublicEDKey` in `Info.plist`). Export for CI with `generate_keys -x <file>`. This is independent of the code-signing cert, so the self-signed→Developer ID switch is seamless for already-installed testers (Sparkle validates the unchanged EdDSA key).

### Distribution & auto-update (Sparkle + Cloudflare R2)

- **Hosting:** R2 bucket **`whisper-master-macos`** in the **corkkam** Cloudflare account (account id `30161a14ccac8ee866a2e85e20a23c78`), served publicly via **`https://dl.corkkam.com`**. S3 (upload) endpoint `https://30161a14ccac8ee866a2e85e20a23c78.r2.cloudflarestorage.com`. Credentials in `.env` (git-ignored; template `.env.example`): `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ENDPOINT`, `R2_BUCKET`, `R2_PUBLIC_BASE_URL`. All three channels (stable/beta/dev) live at this one bucket root, separated by appcast filename.
- **⚠️ The public host is baked into shipped bundles in three places** — `Scripts/channel.sh` (`CH_SU_FEED_URL`, → `SUFeedURL` at build time), `Sources/WhisperMaster/Auth/BetaAccess.swift` (`UpdateChannel.feedURLString`, the runtime override), and `Sources/WhisperMaster/ModelInstall/ModelInstaller.swift` (`mirrorBaseURL`, the `models/` mirror). `R2_PUBLIC_BASE_URL` in `.env` must name the **same host**, or `generate_appcast` writes enclosure URLs pointing somewhere the app never polls. Changing hosts means editing all four together **and** copying `models/` to the new bucket first — a build whose `models/` prefix is empty silently degrades every user to the slow HuggingFace fallback.
- **History:** hosting moved off the earlier `whisper-master` bucket (`model.scoopscore.in`, account `db4d52d…`) in a deliberate **hard cutover** — apps at **1.2.8 and earlier poll `model.scoopscore.in` forever** and will never see another Sparkle update; those installs must be replaced from the DMG link by hand. Then on **2026-08-04** the public host moved again, `pub-98e94…r2.dev` → **`https://dl.corkkam.com`**, a custom domain on the *same* bucket — so `models/` and every artifact came along unchanged (a DNS/alias change, not a data migration), and it picks up edge caching while escaping r2.dev's public-bucket rate limits. Both moves were safe to make abruptly because there is **no installed user base** to strand.

- **⚠️ `model.scoopscore.in` is still live and still needs decommissioning** (verified serving `200` on 2026-08-04, after this was believed handled). It answers with the 1.2.8 appcast, a valid `sparkle:edSignature` **signed by the retired/exposed key**, and `WhisperMaster-1.2.8.zip` beside it. So every 1.2.8 install still has a working update path whose trust anchor is a key that leaked. Taking the host down is what closes that; rotating the key did not, because 1.2.8 bundles carry the *old* `SUPublicEDKey` baked in and will never see the new feed. Re-check with `curl -sS -o /dev/null -w '%{http_code}' https://model.scoopscore.in/appcast.xml` — expect a failure, not a `200`.
- **⚠️ The EdDSA signing key was rotated on 2026-08-04** after the previous key was exposed. It lives in the **login keychain** locally and in the **`SPARKLE_ED_PRIVATE_KEY` GitHub Actions secret** on CI — and nowhere else. It must never go back into `.env`: `release.sh` sources `.env` with `set -a`, so a key there is exported on local runs too, which is why line ~89's CI branch is gated on `$CI`. `SUPublicEDKey` in `Resources/Info.plist` must match whatever signs the appcast, or `generate_appcast` silently omits `sparkle:edSignature` and the guard at line ~124 aborts the release.
- **Layout on R2:** `appcast.xml` + `WhisperMaster-<version>.zip` (Sparkle) + `WhisperMaster.dmg` (stable share link) + `WhisperMaster-<version>.dmg` (versioned share copy) at the bucket root; model archives under `models/`.
- **`release.sh`** = build+sign (`bundle.sh`) → zip → Sparkle `generate_appcast` (EdDSA-signs, sets the enclosure URL via `--download-url-prefix`) → `rclone` upload of the staged dir. It reads `.env` locally; in CI it reads the same vars from the environment and the EdDSA key from `SPARKLE_ED_PRIVATE_KEY` instead of the keychain.
- **Shareable DMG (direct download, separate from Sparkle):** `Scripts/publish-dmg.sh` runs **after** `release.sh` (CI step "Publish shareable DMG to R2", and callable locally) — it reuses the app `release.sh` already built+notarized+stapled, wraps it in a **notarized+stapled** DMG (`make-dmg.sh REBUILD=0`), and `rclone`-uploads it under a **stable** key `WhisperMaster.dmg` (always the newest — this is `https://dl.corkkam.com/WhisperMaster.dmg`, the link you hand people) **plus** a versioned `WhisperMaster-<version>.dmg`. `notarize.sh` is **idempotent** (skips any artifact already carrying a valid stapled ticket via `stapler validate`), so the already-stapled app isn't re-notarized — only the fresh DMG pays a notary round-trip. That extra round-trip is the cost: every version-bump release adds ~5–15 min of notary wait (macOS runner minutes bill ~10×). **⚠️ Overwriting the stable DMG name is NOT safe, contrary to what this line said until 2026-08-04.** The claim was that R2 custom domains return `cf-cache-status: DYNAMIC` and therefore serve the overwrite fresh. That is wrong: **`DYNAMIC` on a HEAD response says nothing about the GET path.** Measured on 2026-08-04, minutes after `publish-dmg.sh` uploaded 1.2.9 to both keys:

- `HEAD dl.corkkam.com/WhisperMaster.dmg` → new object (`content-length: 21010237`, new ETag)
- `GET dl.corkkam.com/WhisperMaster.dmg` → **stale 1.2.8 body** (`20624722` bytes)
- `GET dl.corkkam.com/WhisperMaster.dmg?cb=<ts>` → new object
- `GET dl.corkkam.com/WhisperMaster-1.2.9.dmg` → new object

Both keys held the identical (correct) object at origin — same ETag — so the upload was fine and the *edge* was stale. The consequence was live: the landing page kept handing out 1.2.8, which carries the retired `model.scoopscore.in` feed and the **exposed** `SUPublicEDKey`, i.e. exactly the build the key rotation was meant to retire.

**A Cloudflare cache purge for that exact URL does fix it** — confirmed on 2026-08-04: after purging, a plain `GET` on the alias returned the 1.2.9 object and the mounted image reported `1.2.9` with the rotated `SUPublicEDKey`. So the alias is usable *provided the purge happens every release*. It is currently a manual step, which is why the landing page links the versioned key instead.

**Required after every `publish-dmg.sh` run, until the purge is automated:**

1. Purge `https://dl.corkkam.com/WhisperMaster.dmg` (Cloudflare → Caching → Purge Cache → custom URL). Purge `WhisperMaster-beta.dmg` too on a beta release — it is the same kind of overwritten alias with the same hazard.
2. Verify with a **fresh `GET`, never a `HEAD`** — `HEAD` reported the new object throughout the incident while `GET` served the old body.
3. Verify *contents*, not size: download, `hdiutil attach`, and read `CFBundleShortVersionString` and `SUPublicEDKey` from the mounted app. **`stapler validate`, `spctl`, and byte-length checks all pass on the stale build too**, because the old DMG is validly signed and notarized — none of them distinguishes versions. This is the check that caught the incident; the others said everything was fine.

`lib/config.ts` in the landing-page repo currently points `downloads.stable` at the versioned key, so **it must be bumped on each stable release**. Automating the purge (Cloudflare API token in `.env`, `curl` against `/purge_cache` as the last step of `publish-dmg.sh`) is what would let it go back to the always-newest alias and remove that manual bump.
- **Versioning:** bump **both** `CFBundleShortVersionString` and `CFBundleVersion` in `Resources/Info.plist` before a manual release, or Sparkle won't treat it as newer.
- **⚠️ Never republish a version number.** Each release must use a *new* `CFBundleShortVersionString`, because the archive filename is `WhisperMaster-<version>.zip`. Re-shipping the same version overwrites that file with different bytes while testers/CDN may still hold the old ones — the appcast's `sparkle:edSignature` is computed for the *new* bytes, so Sparkle downloads (possibly Cloudflare-edge-cached) mismatched bytes and fails with **"The update is improperly signed and could not be validated."** This bites silently after a **`git revert`**: the revert changes the code but leaves `CFBundleShortVersionString` unchanged, so the next CI run rebuilds the *same* version with different content. **Fix when it happens:** bump to a fresh version (new filename Cloudflare has never cached) and ship that — do **not** try to re-upload the broken version. The signing certs/EdDSA keys are almost never the actual cause; verify by comparing the served zip's `sign_update` signature against the appcast before blaming signing.

### CI/CD (GitHub Actions)

- Repo is **private** (`corkkam/whisper-master`); the GitHub **default branch is `dev`**, which is where active work lands. `main` is the production branch but *not* the default, so a `gh pr create` with no explicit base targets `dev` — which is right for a feature, and wrong for a release. Name the base when you mean `main`. Being private on a free plan, the repo **cannot carry branch protection or rulesets** (`/branches/main/protection` → 404, `/rulesets` → 403 "Upgrade to GitHub Pro"), so every rule below is convention enforced by you and your agents, not by the server.
- **`.github/workflows/release.yml`** has two jobs. A cheap **`gate`** job (Ubuntu, 1× billing) checks whether `CFBundleShortVersionString` changed versus `github.event.before`; only if it did (or on manual `workflow_dispatch`) does the **`release`** job run on **`macos-26`** (arm64, Xcode 26.x — the toolchain the app is developed against; **not `macos-15`**, whose Xcode 16.4 cannot resolve this project's package graph at all, which is why 1.2.9 and 1.2.10 had to be cut by hand from a local checkout): checkout → `brew install xcodegen rclone` → import the **Developer ID** cert from secrets into a temporary keychain → set `CFBundleVersion` to **epoch seconds** (`date +%s`) so it always strictly increases and can't be undercut by an earlier manual build → **resolve the channel from the branch** → decode the notary `.p8` → run `release.sh` + `publish-dmg.sh` (which build+sign+**notarize+staple**s). Add **`[skip release]`** to the commit message to skip even a version-bump push.
- **Branch → channel (the workflow triggers on pushes to both `dev` and `main`):** a version-bump push to **`dev`** ships the **dev** channel (`CHANNEL=dev` → `appcast-dev.xml` + `WhisperMaster-dev.dmg`, served on the development deployment); a version-bump push to **`main`** ships the **stable** channel (`CHANNEL=stable` → `appcast.xml` + `WhisperMaster.dmg`). The `Resolve release channel from branch` step maps `github.ref_name` → `CHANNEL` and exports it to `$GITHUB_ENV`. The **beta** channel is a separate **manual** flow (`CHANNEL=beta`), never fired by CI. The Telegram announcement runs **only** for stable releases (dev builds are internal); dev-channel versions must carry a `-dev.N` pre-release tag (enforced by `release.sh`).
- **Required repo secrets:** `DEVELOPER_ID_CERT_P12_BASE64` (base64 of the Developer ID `.p12`), `DEVELOPER_ID_CERT_PASSWORD`, `NOTARY_KEY_P8_BASE64` (base64 of the App Store Connect `AuthKey_*.p8`), `NOTARY_KEY_ID`, `NOTARY_ISSUER`, `SPARKLE_ED_PRIVATE_KEY`, plus the five `R2_*` values above. (The CI workflow decodes the `.p8` to `$RUNNER_TEMP` and exports `NOTARY_KEY_P8` for `notarize.sh`.)
- macOS runner minutes bill **~10×** and the Apple notary wait keeps the runner allocated for the whole submission (often 5–30 min today), so each release run is expensive (~hundreds of billed minutes). The **version-bump `gate`** is the primary cost guard — a normal `dev` push that doesn't change `CFBundleShortVersionString` only burns a few Ubuntu seconds; `[skip release]` remains a manual override.
- **Two independent skip switches (don't confuse them):** `[skip release]` skips the *whole* macOS `release` job (no build/sign/notarize/upload — nothing ships). `[skip announce]` still runs the full release (builds, signs, notarizes, uploads to R2 — testers **do** get the Sparkle update) but skips **only** the final Telegram announcement step (`if: !contains(head_commit.message, '[skip announce]')`). So to ship a build without posting to the group, bump the version **and** add `[skip announce]`.
- **`[skip ci]` — the hardest off-switch (GitHub-native, not ours):** putting `[skip ci]` (or `[ci skip]` / `[no ci]`) in the HEAD commit message makes GitHub **not start the workflow at all** — not even the cheap Ubuntu `gate` job. Use this when landing infra/docs/CI-config changes on `dev` that should NOT trigger any run (e.g. a non-version-bump push you just want stored). `[skip release]` still boots the gate; `[skip ci]` skips the entire workflow. It's a per-commit switch, so the *next* normal push runs CI as usual.

### Branching, versioning & beta channel (Git Flow)

**This is a macOS-only app.** There is no iOS target and no TestFlight/App Store pipeline — distribution is Developer ID + notarization + Sparkle/R2 (above). Don't add iOS/TestFlight instructions here; if an iOS target is ever added it gets its own section.

**Branching model — Git Flow, adapted to this repo's wiring.** Roles, not a rename: the existing long-lived branches keep their current names because CI and the Vercel dashboard are wired to them (`dev` auto-deploys the eval dashboard and is what the release `gate` watches — see CI/CD above; renaming it breaks both).

- **`main`** — production. Only ever the tagged, shipped state. Never commit directly; it only receives merges from `release/*` and `hotfix/*`.
- **`dev`** — Git Flow's *develop*: the integration branch, and GitHub's default branch. Features land here; it is also the branch the CI release `gate` watches for a `CFBundleShortVersionString` bump. Treat it as always-releasable.
- **`feature/<slug>`** — cut from `dev`, PR back into `dev`. One concern per branch. **`<slug>` is a plain kebab-case description; no ticket id.** (`feature/notch-agent-surface`, `feature/whatsnew-app`.) This repo does **not** use the machine-wide `<feature|bug>/<COR-###>-<slug>` form from `~/AGENTS.md` — that rule is for the Linear-tracked repos, and the repo's own convention wins here. A bug branch is `fix/<slug>`.
- **`release/<x.y.z>`** — **conditional, not automatic.** Cut one only when work must keep landing on `dev` while a version stabilizes. It buys isolation and nothing else, so if `dev` is going to stay quiet until you ship, skip it: bump on `dev`, dogfood on the dev channel, then merge `dev` into `main`. When you do cut one: bump `CFBundleShortVersionString` + `CFBundleVersion` in `Resources/Info.plist`, finalize the announcement commit body, fix only release-blocking bugs on it, and merge into **both** `main` and back into `dev` when green. **A release branch that `dev` has overtaken is doing no work** — `release/1.1.0` sat for weeks holding zero commits `dev` did not already have, while `dev` moved past it, which reads as "1.1.0 is being stabilized" when nothing was. Finish it or delete it; never leave it.
- **`hotfix/<x.y.z>`** — cut from `main` for an urgent production fix, bump the patch version, then merge into **both** `main` **and** `dev`.
- **⚠️ No branch survives its own merge.** Merging and deleting are **one step**, not two: `git push origin --delete <branch>` goes in the same breath as the merge, and a PR is merged with delete-branch on. This is not tidiness. Thirteen fully-merged branches accumulated here, and two of them were `release/1.2.9` and `release/1.2.10` — numbers *higher* than the live 1.1.0 line, because versioning restarted at 1.0.0. Anyone reading `git branch -r` got the release history backwards. A merged branch carries no commits and only misinformation. (Both were deleted on 2026-08-14 after verifying their tips were ancestors of `main`, `dev`, and every tag.)

**How Git Flow maps onto the CI trigger (important, non-obvious).** CI ships from a **version-bump push to `dev` OR `main`** (the `gate` job runs on both), *not* from tags. The branch decides the channel: a bump on **`dev`** ships the **dev** channel (the integration/development build, served on the dev deployment); a bump on **`main`** ships the **stable** channel (the production build). Beta remains the manual `CHANNEL=beta` side-track. (If the branch→channel wiring changes, update this paragraph and `release.yml`'s `Resolve release channel from branch` step together.)

**The flow, start to finish — there is exactly one.** Four moves, and only the last one reaches users:

| # | Move | What ships |
|---|---|---|
| 1 | `feature/<slug>` off `dev`, PR back into `dev`, **delete the branch in the same step** | nothing (the `gate` sees no version bump and exits in seconds) |
| 2 | Bump `CFBundleShortVersionString` to `X.Y.Z-dev.N` on `dev` and push | **dev channel** — CI builds, signs, notarizes, uploads `appcast-dev.xml`, tags `vX.Y.Z-dev.N`. No Telegram post. |
| 3 | *(optional)* `CHANNEL=beta bash Scripts/release.sh` from a local checkout at `X.Y.Z-beta.N` | **beta channel** — manual, never CI |
| 4 | Merge into `main` at the finalized `X.Y.Z`, push | **stable channel** — CI ships it, posts to Telegram, and tags `vX.Y.Z` |

A `release/<x.y.z>` branch is an **optional detour between 1 and 4**, taken only when `dev` must keep moving during stabilization. Merge it into `main` **and** back into `dev`, then delete it.

**Three things that decide whether a push ships anything**, in the order CI checks them: `[skip ci]` in the commit message stops the workflow before it starts (not even the Ubuntu gate); an unchanged `CFBundleShortVersionString` stops it at the gate; `[skip release]` stops the macOS job after the gate. To land work with no risk of a build, change no version and add `[skip ci]`.

**⚠️ Standing freeze as of 2026-08-14: no stable release.** `main` is at `1.0.1`; `dev` is at `1.1.0-beta.6` and ~76 commits ahead. Do **not** merge anything into `main`, and do **not** bump `CFBundleShortVersionString` on `dev` — either one ships a build. If a release run starts by accident, stop it (`gh run cancel`) rather than letting it finish. Lift this line only when the owner says so.

**Versioning — SemVer, every release tagged.**
- `CFBundleShortVersionString` is **SemVer** `MAJOR.MINOR.PATCH` (the human version, e.g. `1.2.6`). `CFBundleVersion` is the monotonic build number — CI sets it to epoch seconds so it always strictly increases (see CI/CD); locally bump it yourself.
- **`Resources/Info.plist` is the only version source.** `project.yml` deliberately carries **no** `MARKETING_VERSION` or `CURRENT_PROJECT_VERSION`: `GENERATE_INFOPLIST_FILE: NO` plus literal plist keys mean no build setting is ever interpolated, so a copy there is inert and can only mislead. It did: the copies said `1.2.10` while the plist said `1.1.0-beta.6`, i.e. the dead number was the higher one. Both were removed on 2026-08-14 — don't add them back. (`release.sh` still exports its own `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` to the PostHog symbol uploader; those are read from the built app's plist, not from the project.)
- **Every release is tagged `vX.Y.Z`, and CI does the tagging.** The `Tag the release` step (last in `release.yml`, after the announcement so the tag can't shrink its own notes range) reads `CFBundleShortVersionString` and pushes `v<version>` at the released SHA. It is idempotent — an existing tag is skipped — and the push trigger is branches-only, so it can't loop. **Don't tag by hand after a CI release**; the tag is already there, and a second annotated tag at the same name only fails. Hand-tagging (`git tag -a v1.2.7 -m … && git push origin v1.2.7`) is for the **manual** flows only: a beta cut, or a release built locally. Pre-releases are `vX.Y.Z-beta.N` / `vX.Y.Z-dev.N`. The tag is the anchor the Telegram fallback release-notes use (`git log <last v* tag>..`), so an untagged manual release degrades that fallback.
- **Never republish a version number** — see the ⚠️ note under Distribution. A new release always means a new `X.Y.Z` (hence a new tag and a new archive filename).

**Beta channel (Sparkle, ONE bundle) — implemented (single-appcast, channel-tagged).** A pre-release track a user is put on **server-side**, that never disturbs stable users and needs **no reinstall in either direction**. Driven by a `CHANNEL` env var (default `stable`, one of `stable|beta|dev`) resolved in **`Scripts/channel.sh`** and sourced by `bundle.sh`/`release.sh`/`make-dmg.sh`/`publish-dmg.sh`. How the pieces fit:
- **⚠️ Beta is byte-identical to stable in identity.** Same bundle id (`app.whispermaster.mac`), same `.app` name, same `SUFeedURL`. It differs ONLY by the `-beta.N` marker in `CFBundleShortVersionString` and by `<sparkle:channel>beta</sparkle:channel>` on its appcast item. This is load-bearing: Sparkle installs an archive only if it holds a bundle matching the host's **file name or bundle id** (`SUInstaller.installSourcePathInUpdateFolder`), so the moment beta carries its own id it can neither update a stable install nor be updated by one. `bundle.sh` therefore re-badges **`dev` only**.
- **One feed, two kinds of item.** `release.sh` seeds `build/sparkle` with the **already-published** `appcast.xml` before staging the new zip, then runs `generate_appcast --channel beta`. Sparkle offers an **untagged** item to everyone and a **tagged** one only to an updater that allows that channel (`SUAppcastDriver.m` ~487), so one file serves both tracks: a stable user never sees beta items; a beta user sees both and takes the higher `CFBundleVersion`.
- **⚠️ The seeding step is not optional.** `generate_appcast` rebuilds the feed from the archives it finds, so an unseeded stage yields a one-item appcast — uploading that deletes every older item and strands anyone who has not updated. Seeded, it reports "removed 0 old updates" and copies prior items through verbatim, signatures and all, without their archives on disk.
- **The runtime half is `allowedChannelsForUpdater:`, not a feed override.** `AppDelegate` returns `BetaAccess.allowedChannels` — `["beta"]` for a flagged user, empty otherwise. **Empty means "stable only", not "no updates"**: the default channel is always allowed. There is no `feedURLString` override any more; the old one pointed beta users at `appcast-beta.xml`, which served a `…mac.beta` bundle their `…mac` install could never accept, so the update was offered, downloaded, then refused.
- **Reversible with no downgrade support.** CI stamps `CFBundleVersion` with `date +%s` (`release.yml`), so versions only increase in build order. Flag on → the next check finds the newer beta. Flag off → the beta item leaves the candidate set and the user stays put until the next stable, built later and numbered higher, pulls them back. Sparkle cannot downgrade, and does not need to.
- **`ReleaseChannel` keys on the VERSION, not the bundle id** (the id can no longer tell stable from beta). A marker-less version is `.stable`, so a forgotten bump can only close the gated surfaces, never open them. Beta still uses the production Clerk instance + `public` schema.
- **Release plumbing.** `CHANNEL=beta bash Scripts/release.sh` builds, signs, generates the merged `appcast.xml` and uploads it + `WhisperMaster-<ver>.zip`. `release.sh` **requires** the `-beta.N` marker (else it aborts), and its signature guard is scoped to **this release's enclosure line** — a file-wide grep passes on a merged feed because older items are already signed, which is the exact failure the guard exists to catch. `CHANNEL=beta bash Scripts/publish-dmg.sh` wraps the same app as **`WhisperMaster-beta.dmg`** — still needed, because it is the one-time manual download that moves a legacy side-by-side tester onto the unified build. Beta is a **manual** flow (not wired into CI).
- **Legacy `…mac.beta` installs cannot be migrated by an update** and are frozen at 1.1.0-beta.8 forever. `appcast-beta.xml` stays published, untouched, until analytics shows nobody is on `<= 1.1.0-beta.8`; then delete it.

- **Dev channel (`CHANNEL=dev`) — the third, CI-driven channel.** Same machinery as beta but for the development build: app "Whisper Master Dev", bundle id `app.whispermaster.mac.dev`, feed `https://dl.corkkam.com/appcast-dev.xml`, DMG `WhisperMaster-dev.dmg`. Unlike beta, it **is** wired into CI — a version-bump push to the `dev` branch ships it (see CI/CD). A `.dev` bundle always polls the dev feed regardless of the Clerk `betaAccess` flag: `BetaAccess.currentChannel` pins the channel by bundle id (the dev channel is gated by branch/environment separation, not the per-user flag). Versions must carry `-dev.N`. Served on the separate development landing-page deployment.
- **Promotion = Git Flow.** A `release/x.y.z` branch is dogfooded via the beta channel (or on `dev` via the dev channel); when it's proven, merging the finalized `X.Y.Z` into `main` ships the *stable* build (per the CI mapping above) and tag `vX.Y.Z` records it. Betas are the `-beta.N` pre-release tags; dev builds are `-dev.N`.
- **Alternative (Sparkle-native channels):** instead of a second appcast, keep one `appcast.xml` and tag beta items `<sparkle:channel>beta</sparkle:channel>`, with beta builds opting in via `SPUUpdaterDelegate.allowedChannels`. Equally valid; the separate-appcast route was chosen because it's a smaller change to the existing single-feed `release.sh`.

### Release announcements (Telegram) — the commit message IS the post

After a successful CI release, `Scripts/notify-telegram.py` (final step in `release.yml`) posts to the Telegram group `Corkkam.com` (chat id stored in the `TELEGRAM_CHAT_ID` secret; bot token in `TELEGRAM_BOT_TOKEN`) **and attaches the built app zip** (`build/sparkle/WhisperMaster-<version>.zip` — the Sparkle archive, i.e. the actual `.app`, not a DMG) so people download it straight from the group. **No LLM is involved** — the announcement text is taken verbatim from the release commit message, so write that message as finished, post-ready copy:

- The **body** of the release commit (everything after the subject line) is posted verbatim as the announcement, then reused for X/Twitter. **Write it like a human tweeting, not like release notes.** This is the part to get right — the default tone tends to read AI-generated; actively avoid that:
  - Sound like a person: casual, first-person-ish, contractions, plain words. Lowercase-y is fine. Short punchy lines.
  - Lead with the single thing a user actually cares about. Don't open with a tidy headline like "Fresh X and smoother Y."
  - **Banned AI tells:** the "This release redesigns/introduces/brings…" framing, balanced tricolons (three things joined by em-dashes), "now with X" parentheticals, "seamless/effortless/powerful/robust," marketing CTAs ("Download right here"), and more than one emoji.
  - **No dashes.** Don't use em dashes (—) or hyphens as sentence punctuation in the announcement. Break the thought into separate sentences with periods or commas instead. (Dashes read as an AI tell.)
  - Keep it short enough to paste into X (a few lines, well under 280 chars). No hashtags, no markdown. Don't claim features that aren't in the release.
  - **Bad (AI slop, don't do this):** "Fresh onboarding and smoother updates. This release redesigns the first-run setup (now with a notifications step), makes update alerts actually show up, and adds a gentle nudge when a Bluetooth mic is hurting audio quality — one tap switches you to the built-in mic. Download the app right here. 🎙️"
  - **Good (human, tweetable):** "new build's up 🎙️ setup's way cleaner, update alerts actually fire now, and if a bluetooth mic is wrecking your audio it'll nudge you to switch to the built-in one (one tap). file's attached, give it a spin."
- If the release commit has **no body**, the script falls back to a `🚀 Whisper Master <version>` heading plus a bullet list of the commit subjects since the last `v*` tag — so even subjects should read as user-facing release-note lines (`Merge`, `release:`, `bump`, and `[skip release]` commits are filtered out).
- The version header and download link are NOT auto-added when a body is present — put whatever headline/version mention you want in the body itself. A `[skip release]` trailer is stripped from the posted text.
- The step is `continue-on-error` and no-ops without the Telegram secrets, so a notification hiccup never fails a release.
- **To release without announcing:** put `[skip announce]` in the commit message. The release job still builds/signs/notarizes/uploads (the Sparkle update ships to testers) — only this Telegram step is skipped. This is distinct from `[skip release]`, which skips the entire release.

**Publishing a model to R2** (separate from app releases): from `~/Library/Application Support/FluidAudio/Models`, `ditto -c -k --keepParent <dir> <dir>.zip`, then `rclone` it to `whisper-master/models/` (creds from `.env`). Done for the engine (`parakeet-tdt-0.6b-v3`) and CTC (`parakeet-ctc-110m-coreml`) models; the app installs them mirror-first via `ModelInstaller`.
